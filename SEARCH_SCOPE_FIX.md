Rentee property-search fix — implementation report

1. Single-Condo root cause: `lead_with_active_search_filters` copied the historical Lead and replaced `Geo` without clearing `preferredCondos` when active `selected_condos` was empty. `structured_lead_requirements` retained those historical Condo IDs; `build_listing_bubble_constraints` gave them precedence over Geo. This was stale-scope leakage, not a helper selecting the first Condo in a Geo. Independently, the old area query used Listing.Geo directly instead of expanding Condo.Geo.

2. Unexpected ID: with the supplied `condo_scope=[]` log, `1775029792997x369997404181102600` reaches the constraint through `Lead.preferredCondos -> preferred_condo_ids -> condo equals`. There is no hard-coded occurrence in the application or fixtures. The production Lead record is not available in this workspace, so the Condo's name and the historical operation that saved the ID cannot be independently established here.

3. Incorrect entity typing: `advance_property_search` accepted `preferred_condo_names` without requiring Bubble IDs. It also reclassified Geo candidates using `resolve_condo_names`, which reads the advisory CSV spreadsheet, not Bubble Condo records. `_apply_current_search_location` logged advisory matches as resolved Condos. Neither successful string normalization nor a spreadsheet row established database identity.

4. Continuation overwrite: the tool received model arguments without a current-message grounding check. Nonempty proposed Condo names reset the area and replaced selected Condos. Separately, `search_listings=True` invoked full-shortlist selection and promoted recommendations into active scope. Both paths could mutate constraints without explicit selection.

5. Files/functions: `app.py` changes `advance_property_search`, `execute_chat_tool`, `_apply_current_search_location`, `lead_with_active_search_filters`, `build_listing_bubble_constraints`, `get_plausible_listings`, and `match_lead`; adds `grounded_search_update`, `resolve_search_entities`, and `get_geo_condo_ids`. `test_search_flow.py` updates obsolete expectations and relationship fixtures. `test_search_scope.py` adds 19 regressions. No Lead schema migration is introduced.

6. Area retrieval: resolve Geo IDs, page all Condo records constrained by `Geo`, collect every matching `_id`, then query Listing.`condo` in batches of up to 50 IDs. A singleton uses equality. Existing transaction/property/bedroom constraints and Python validation remain. Listings need no direct Geo value. Empty Geo membership returns no matches without a Listing query. Bubble documents `in` for all field types: https://manual.bubble.io/core-resources/api/the-bubble-api/the-data-api/data-api-requests#constraint-types . This avoids one Listing request per Condo and bounds query URL size. The existing candidate limit still bounds retrieval after enough unseen plausible matches are collected.

7. Active merging: the chat dispatcher passes the actual latest user message internally, overriding any model-provided copy. Grounding retains location candidates mentioned in that message and only scalar fields with corresponding current-turn evidence; other fields inherit active state. Database validation precedes persistence. Reclassification also corrects incompatible reset modes. Saved active state owns location, transaction, bedrooms, and budgets, including empty values; historical Lead fields remain separately persisted. Legacy searches without saved active filters retain their existing fallback.

8. Authoritative resolution: both candidate lists pass through the same resolver. Geo normalization/fuzzy suggestions must map to a real Bubble Geo ID; Condo candidates must map to a real Bubble Condo ID. A Geo-only match becomes an area even when proposed as a Condo. A real match in both types asks for clarification. Logs distinguish candidate, normalized text, proposed type, database matches, and resolved IDs. Advisory location logs now say resolution is pending.

9. Alternatives: a continuation without constraint evidence preserves active scope. Recommended Condos are no longer automatically selected. Existing Folio Listing IDs are excluded during retrieval before the candidate target and again before ranking, allowing later pages to supply unseen matches. Exhaustion offers an area/budget adjustment without applying one. Condo-advice refreshes also preserve explicit selected scope.

10. Unresolved candidates: unmentioned inferred locations are discarded before lookup. Explicit unknown/ambiguous locations return clarification without saving invalid scope or querying Listings. Unresolved saved scope fails closed. A legacy Condo query containing a Geo-only name is reclassified through the Geo-to-Condo path. Partial resolution cannot silently broaden active scope.

11. Full scans: the failed-Condo full-scan fallback is removed. Scoped searches use Condo relationship constraints. An intentionally unrestricted search can still query across inventory, with existing structured filters and the candidate limit; this is explicitly logged as `reason=no_location_constraints`.

12. Regression coverage: Mont Kiara, Bangsar, Damansara Heights and a synthetic future Geo each contain three Condo fixtures and multiple Listings without Listing.Geo. Additional tests cover buy-to-rent inheritance; eight continuation phrasings with invented arguments; Folio-style exclusions and pagination; explicit Condo and Area switches; wrong entity labels and reset modes; unknown, deleted, empty, ambiguous and ID-less entities; typo grounding; and 123-ID batching. Existing tests that required historical scope leakage or automatic shortlist promotion now assert the requested behavior.

13. Validation: `python3 -m unittest discover` — 616 tests, 1.345 seconds, OK (zero failures/errors). `git diff --check` — clean. Tests use mocked Bubble-shaped records; no live Bubble requests, production writes, or deployment were performed. Live API behavior and production relationship records were not independently verified.
