Rentee saved-state recovery and adjacent-area broadening

1. Why corruption survived: the previous fix validated incoming tool candidates, while `load_active_search_state` decoded saved JSON without validating its entity types. Continuations correctly inherited that JSON, including previously corrupted selected Condos. Query construction rejected them, but did not repair persistence.

2. Loaded-state validation: effective search paths now validate saved areas against Bubble Geo records and selected Condos against Bubble Condo records, requiring IDs. Failed typed matches are checked against the other entity type and logged. Invalid entries are removed from effective scope and obsolete shortlist entries. An invalid-only scope requires clarification, never an unrestricted Listing query. Lookup transport errors preserve the saved geography and temporarily block retrieval rather than deleting valid data.

3. Provenance: search JSON contains `geography_provenance`, with `source` (`explicit_user` or `inherited_explicit`), the current-turn user evidence, and a `last_explicit` snapshot of areas and selected Condos. Explicit snapshots are retained in both active state and structured brief. Model-only updates cannot replace a recorded explicit scope. Suggested adjacent geography is stored separately in `pending_broadening`; it is not an active constraint. Legacy unprovenanced values are not retroactively labelled explicit.

4. Recovery: invalid saved scope first tries the validated explicit snapshot in active state, then the snapshot in the brief. This restores the last explicit geography while retaining transaction, bedrooms and budgets. A valid remaining current area also survives removal of a bad Condo. The historical cumulative area list does not identify which area was last explicitly requested, so it is deliberately not used to guess. Old corrupted records without sufficient evidence are cleaned, logged as unrecoverable, and ask for a location. Repairs are persisted by the advance and direct matching paths.

5. Database truth: the existing incoming-candidate resolver continues checking both actual entity types. Saved-state validation separately checks the stored type first. A stored Geo-only name is rejected as a Condo; it is not silently promoted to a newly requested area. Direct matching also replaces stale passed Condo scope with the validated saved scope, preventing a caller from reintroducing the rejected name.

6. Field spelling: the implementation uses `Adjacent_geos` exactly. Schema documentation records `Geo.Name`, `Geo.Adjacent_geos` and `Condo.Geo`; Geo name readers retain the existing legacy `name` compatibility. These spellings follow the supplied schema and existing repository access patterns. No Bubble token is available locally, so an authenticated live API response could not independently confirm the populated fields.

7. Loading adjacency: resolve current Geo IDs, read their Geo records, read the `Adjacent_geos` relationship IDs, deduplicate them, exclude already-current IDs, then load the related Geo records for actual IDs and names. No coordinates, static name lists, or Python adjacency map are used. Missing adjacency returns the existing generic adjustment offer; API errors do not broaden scope.

8. Offering adjacency: only the no-unseen-matches branch of `match_lead` calls adjacency loading. Valid current Condo-only scopes do not automatically become area searches. The response names the adjacent options and explicitly offers to add them while retaining other requirements. Pending offers are saved before asking for approval; persistence failure produces the generic response instead.

9. Acceptance: a short affirmative response can accept an outstanding offer for the same Folio and unchanged geography, within 15 minutes. Acceptance adds the offered areas to the current areas, validates them again, records explicit-user provenance, and clears the offer. The offer is one-use; a different search turn clears it. Bare approval without a valid offer does not broaden. Naming a particular area is a normal explicit replacement and does not require adjacency. Offers are bound to search interactions; this change does not add a general conversation-wide approval subsystem.

10. Multiple Geos: accepted areas use the existing `Geo -> every matching Condo -> Listing.condo` path. Listing retrieval remains constrained to batches of Condo IDs. Adjacent IDs never become Condo names. Existing Folio exclusions continue finding unseen results before broadening is offered.
